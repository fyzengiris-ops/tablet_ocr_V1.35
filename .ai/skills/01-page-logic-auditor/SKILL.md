# 页面逻辑审核 Skill

## 目标

从产品设计者、测试者、PC/Pad 业务一致性对照者三个视角审核当前平板端 OCR 页面。不要直接改页面，也不要直接生成最终 PRD。核心目标是发现页面里还没有明确的业务逻辑、边界场景、异常处理、交互规则，以及 Pad 与 PC 对应能力之间的业务差异，并把这些问题整理成用户可以快速决策的选项。

执行前必须先读：

```txt
.ai/skills/shared/project-context.md
```

并遵守与 Skill0 的衔接门禁：**没有已确认的对象清单，不得开始本 Skill 的决策题输出。**

## 与 Skill0 的衔接门禁

完整顺序：

```txt
Skill0 对象清单（已确认） -> Skill1 本审核 -> Skill2 …
```

1. 开始前检查是否存在已确认清单：

```txt
产品文档/prd-workflow/inventories/<页面或流程>.inventory.md
```

2. 若清单不存在，或文件中“清单状态”不是已确认：
   - 不要输出 `1A2C3D` 待确认问题。
   - 告知用户需先执行 Skill0。
   - 询问是否现在开始 Skill0。
3. 若清单已确认：
   - 只对清单中的“必审对象”出待确认问题。
   - “可跳过对象”默认不审，除非用户明确要求加入。
   - 审核中若发现清单外仍有关键业务对象，先暂停扩审，建议回到 Skill0 补清单并确认。

## 必须遵循的流程

1. 确认本次要审核的页面或流程范围。
2. 确认页面相关前提信息，例如目标用户、业务背景、当前页面目标、已知约束、重点审核方向。
3. 缺少范围时先问；缺少前提时让用户补充或回复“无额外前提”。
4. 检查 Skill0 已确认清单。
5. 范围、前提、清单都齐全后，用一句话复述本次审核范围、前提和必审对象数量，再开始读取代码。
6. 读取当前 Next.js 项目相关文件，优先：
   - `src/app/tablet-ai-entry/tablet-ai-entry-preview.tsx`
   - `src/components/UploadQuestionDialog.tsx`
   - `src/requirements/*.registry.ts`
   - 与目标对象相关的 `src/components/prd/*.tsx`
7. 按 Skill0 清单中的“PC 对应对象/能力”读取 PC 端对应页面、组件、registry 或历史决策；清单未给出时，用 `rg` 按文案、接口、组件名、需求编号查找。
8. 审核对象以 Skill0“必审对象”为准，在代码中定位对应 UI，覆盖字段、文案、按钮、操作区域、弹窗、Tab、步骤条、列表、空状态、加载态、成功态、失败态、禁用态等。
9. 同时做 PC/Pad 对照：PC 已有且 Pad 无业务差异的口径默认沿用；Pad 因触控、横屏、步骤拆分、画框方式产生的差异，需判断是交互差异还是业务差异。
10. 只输出会影响业务逻辑、PRD 编写、测试验收或后续实现的待确认问题。纯视觉偏好不要提，除非会影响用户理解或操作结果。
11. 用户回复类似 `1A2C3D` 后，解析每个编号选择。
12. 只有当本轮所有待确认问题都有明确决策后，才回显完整决策结果。
13. 用户确认决策结果无误后，才写入 `产品文档/prd-workflow/decisions/<页面或流程>.decision.md`。

## 前置信息检查

开始审核前必须检查两类信息：

1. 页面名称或页面范围  
   示例：`/tablet-ai-entry` 平板端入口、上传资料弹窗、选择识别方式步骤、选择识别内容步骤、校对识别结果步骤。

2. 页面前提信息  
   示例：目标用户是谁、页面要解决什么业务问题、当前版本哪些能力已确定、哪些只是原型占位、这次重点关注哪些逻辑。

如果缺少信息，按下面方式提问：

```md
我需要先确认两项信息，再开始审核：

1. 页面名称/页面范围：<如果已知就写已知内容；未知就请用户补充>
2. 页面前提信息：<如果已知就写已知内容；未知就请用户补充，允许用户回复“无额外前提”>
```

## 首次输出格式

首次审核结果必须用中文，并严格使用下面的一级结构：

```md
一、页面名称
<页面名称或流程名称>（<路由或主要文件路径>）

二、待确认问题
**1、<字段/文案/按钮/某区域>：<对象名称>**

**问题描述：**<说明当前代码已实现什么、还缺少什么业务情景、为什么需要确认。>

**建议方案：**
A. <方案A，写清采用后的业务含义>
B. <方案B，写清采用后的业务含义>
C. <方案C，写清采用后的业务含义>

---

你可以直接回复类似：1A2C3B
```

首次输出规则：

- 编号从 `1` 开始连续递增。
- 每个问题只对应一个字段、文案、按钮、区域或逻辑对象。
- 同一个编号下的方案必须回答同一个决策维度，方案之间必须互斥。
- 凡是方案包含提示、报错、空状态、失败状态、禁用状态、二次确认、拦截或恢复动作，必须写清触发条件和具体提示文案。
- 如果提示文案本身不确定，必须把文案作为该编号下的可选方案，或拆成独立编号让用户确认。
- 只有当“不处理/保持现状”本身是合理产品决策时，才加入这个选项。
- 如果问题太多，优先输出 P0/P1 问题，并说明页面可以分批审核。

## 用户决策回复解析

当用户回复类似 `1A2C3D` 时：

- `1A` 表示第 1 个问题选择 A 方案。
- 支持自定义方案，例如 `3【改成上传前先让用户选择资料类型】`。
- 支持用户对某个编号表示没看懂；此时先解释该编号并要求补齐，不要丢失其他已确认决策。

## 决策确认格式

解析用户选择后，必须用中文回显：

```md
一、页面名称
<页面名称或流程名称>（<路由或主要文件路径>）

二、决策结果
**1、<字段/文案/按钮/某区域>：<对象名称>**

**决策结果：**<选择的方案字母或自定义方案>，<该方案的完整业务含义。>

请确认以上决策是否正确。确认后我会把它沉淀为页面决策记录。
```

在用户确认前，不要写入决策记录文件。

## 决策记录文件

用户确认决策结果后，创建或更新：

```txt
产品文档/prd-workflow/decisions/<页面或流程>.decision.md
```

文件结构：

```md
# <页面名称或流程名称> 决策记录

## 页面范围
- 页面/流程：<名称>
- 路由：<例如 /tablet-ai-entry>
- 相关代码文件：
  - <file>

## 已确认决策
1. <字段/文案/按钮/某区域>：<对象名称>
   - 决策：<选择的方案字母或自定义方案>
   - 结论：<完整业务含义>
   - 影响范围：<页面显示、操作、权限、数据流转、异常处理等>

## 暂不处理
- <如有>

## 待后续确认
- <如有>
```

## 审核关注点

- PC/Pad 一致性：PC 端已有业务口径是否可直接沿用；Pad 是否缺少 PC 已有的限制、提示、流转或异常处理。
- Pad 交互差异：触控画框、步骤拆分、横屏布局、弹窗尺寸、批量选择等差异是否改变业务结果。
- 入口：谁能看到入口、什么时候可点击、关闭后回到哪里。
- 文案：按钮、空状态、提示、状态文案是否和实际行为一致。
- 状态：加载、空、成功、失败、禁用、部分成功、恢复、重复操作是否完整。
- 权限：不同角色、数据归属、受限操作是否需要明确规则。
- 数据流转：文件、切题框、识别结果、题目答案匹配结果如何跨步骤传递。
- 异常：非法输入、缺少输入、接口失败、请求超时、重复提交、不支持文件或数据。
- 隐藏交互：弹窗、悬浮面板、Tab、步骤、Popover、hover 后才出现的操作。
- 校验：当前代码是否阻止不可能或高风险操作。
- 恢复：用户是否能取消、重试、重新上传、继续流程，并避免数据丢失。

## PC/Pad 对照审核规则

默认策略：

1. PC 端已有明确业务逻辑，且 Pad 只是交互适配时，默认沿用 PC 口径，不单独提问。
2. PC 端已有逻辑，但 Pad 页面缺少对应状态、提示、校验或流转时，需要提出待确认问题。
3. Pad 因触控、画框、步骤拆分、横屏布局导致必须改业务口径时，需要提出待确认问题。
4. 找不到 PC 对应能力时，不硬套 PC 逻辑；标记为“未确认 PC 对应项”，并让用户确认是否作为 Pad 独有逻辑。
5. 输出问题时说明对照结果，例如“PC 端已支持 xxx，Pad 当前未体现 xxx，所以需要确认是否沿用”。

## 输出约束

- 面向用户的输出必须以决策为中心。
- 使用页面上的具体对象名称。
- 不要提出“是否优化体验”这类空泛问题。
- 每个选项都必须能成为后续 PRD 或实现决策。
- 除文件路径、代码标识、字段名、命令名等必要内容外，尽量使用中文。
- 审核对象与示例优先使用平板端 OCR 页面；PC 端只作为业务口径基线和对照来源，不照搬 PC 视觉布局或交互形态。
- 对 PC 端已明确且 Pad 无业务差异的规则，不制造无意义确认题；只在缺失、冲突、差异或无法确认时提问。
