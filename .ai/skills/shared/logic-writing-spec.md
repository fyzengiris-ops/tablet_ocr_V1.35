# 业务逻辑写作规范

本规范是 Skill2 / Skill3 / Skill4 / Skill5 / Skill6 的共同源头。当前仓库采用保守方案：用户侧悬浮面板、右侧 PRD 面板、Markdown PRD 中的业务逻辑正文，继续来自需求注册表的 `display` + `operation` 字段。

配合阅读：

```txt
.ai/skills/shared/project-context.md
```

## 1. 总原则

1. **先收集业务规则，再决定放入 `display` 还是 `operation`。**  
   不要先套模板再填空。
2. **内容完整，不只写当前前端已实现。**  
   必须覆盖代码已体现、Skill1 已确认、以及合理延伸的边界场景。
3. **一条业务规则只写一次。**  
   禁止同一规则在 `display` 和 `operation` 中换说法复述。
4. **有规则才写字段，无规则不写空兜底。**  
   不写“无额外权限限制”“无异常场景”“本对象仅展示”等无效说明。
5. **表达短、可验收、产品语言。**  
   不写组件状态、接口名、DOM、缓存键等技术实现细节。
6. **先写完整业务逻辑，再按实际内容生成分组标题。**
   “显示说明”“操作说明”“数据流转”“异常”“统计口径”“数据规则”等只是标题示例，不是固定标题集合，也不是每条需求都必须出现的栏目。

## 2. 正确写作顺序

对每个页面对象，必须按下面顺序执行：

```txt
1) 收集规则素材（来源 A + B + C）
2) 整理成一条条可验收的业务规则
3) 判断每条规则回答的是“展示什么”还是“用户操作/系统流转如何发生”
4) 写入 display.description 或 operation.description
5) 权限、数据流转、异常边界只在确有规则时写入 operation 的对应字段
6) 基于最终保留的业务逻辑归类，并为每个非空分类生成简短、准确的标题
7) 自检：固定套标题、标题与正文不匹配、空兜底、跨字段重复、只写代码表面、该延伸未延伸
```

### 2.1 规则来源

| 来源 | 含义 | 说明 |
| --- | --- | --- |
| A. 代码已体现 | 当前页面已实现的展示、交互、状态和文案 | 必要，但通常不够 |
| B. Skill1 已确认 | 审核决策里已拍板的业务口径 | 硬约束，优先于猜测 |
| C. 合理延伸 | 基于 A+B，该对象常需补齐、且与已确认口径一致的边界场景 | 例如失败重试、数据保留、重复操作、识别结果为空 |

**明确禁止：** 只根据前端现有样式或按钮，把注释写成“当前代码做了什么”的说明书。

### 2.2 合理延伸边界

要写：

- 与已确认主规则直接相关的边界，例如上传失败、识别失败、部分成功、重复点击、关闭弹窗、重新上传、刷新后状态等。
- 该类字段/模块通常必须定清，否则无法验收的规则。

不要写：

- 与 Skill1 已确认口径矛盾的新方案。
- 纯技术实现细节。
- 明确不在本次页面范围的能力。

拿不准且影响验收时：回到 Skill1 确认，不假装代码已实现。

## 3. `display` 与 `operation` 分层

### display 只写展示逻辑

`display` 回答：

- 页面展示什么。
- 什么状态或条件下展示。
- 文案、数量、列表、按钮、禁用态、空状态如何呈现。
- 数据为空、识别中、识别失败、识别完成时用户看到什么。

不要在 `display` 里写用户点击后怎么流转，除非这条规则本质是状态展示。

### operation 只写操作逻辑

`operation` 回答：

- 用户能做什么。
- 点击、上传、切换、删除、重试、加入试卷后发生什么。
- 操作前置条件、拦截、失败提示、结果保存或传递。
- 权限、数据流转、异常处理等确有业务规则的内容。

不要在 `operation` 中重复 `display.description` 已经讲清的展示内容。

## 4. 业务逻辑标题生成规则

标题必须在当前对象的业务逻辑全部整理完成后生成，不能先确定栏目名称再向栏目里填内容。

- 标题应概括该组正文实际回答的问题，优先使用简短的业务维度词，一般控制在 2～6 个汉字。
- 标题可以是“入口展示”“状态规则”“操作说明”“学科流转”“数据规则”“异常处理”“统计口径”等，但示例只用于说明风格，不构成固定枚举。
- 同一页面对象不要求统一使用同一套标题；不同对象应根据各自规则内容分别命名。
- 只有存在对应业务规则时才生成标题和正文；不得为了凑齐常见栏目而补空标题、空说明或兜底句。
- 标题不得只是重复需求对象名称，也不得写成完整句子；应能帮助用户快速判断该组规则的关注维度。
- 当一组正文同时混有两个可独立理解的业务维度时，应先拆分归类，再分别命名；不要用宽泛标题掩盖混合内容。
- `display.title` 与 `operation.title` 应保存本条需求根据正文生成的标题。展示层应读取这些标题，不得统一替换成固定的“显示说明”“操作说明”。
- `permission`、`dataFlow`、`exceptions` 等字段仅在有内容时展示；其展示标题也应以实际语义为准，不把常见字段名视为不可变标题。

## 5. 推荐字段写法

当前 `src/requirements/schema.ts` 使用现有结构，常见写法如下：

```ts
display: {
  title: "资料展示",
  description: [
    "上传资料步骤默认展示本地上传入口、资源库入口和已上传文件列表。",
    "未上传文件时，文件列表展示空状态，不允许进入下一步。"
  ],
},
operation: {
  title: "上传规则",
  description: [
    "用户上传文件并选择学段学科后，下一步按钮才可点击。",
    "上传失败时保留已成功上传的文件，并提示用户重新上传失败文件。"
  ],
  exceptions: [
    "文件格式不支持时，提示用户更换为支持格式，不进入识别流程。"
  ],
},
```

要求：

- 每条描述是一个可验收事实。
- 不手写多层编号，由展示层统一处理。
- `permission`、`dataFlow`、`exceptions` 只在确有规则时写。
- 如果当前 schema 要求字段存在，也不要用空兜底污染用户正文；优先使用空数组或按现有工具过滤。

示例中的“资料展示”“上传规则”只适用于该段示例内容；其他对象必须重新根据自身业务逻辑命名。

## 6. 常用归类参考

- 展示什么、什么状态/条件展示、无数据怎么展示 -> `display.description`
- 用户点击/切换/输入/提交后系统如何响应 -> `operation.description`
- 数据来源、结果保存、跨步骤传递 -> `operation.dataFlow`
- 角色、入口可见性、可操作范围 -> `operation.permission`
- 空数据、失败、超时、重复操作、缺少输入、接口不可用 -> `operation.exceptions`

## 7. 质量自检清单

生成或展示前检查：

- [ ] 是否按「收集规则 -> 分层 -> 写入」执行。
- [ ] 是否同时考虑了代码、Skill1 决策、合理延伸。
- [ ] 是否存在空兜底句。
- [ ] 是否存在跨字段重复。
- [ ] 是否只写了 UI 表象而缺少业务口径。
- [ ] 是否出现技术实现词或空话。
- [ ] 是否先完成业务逻辑归类，再生成与正文匹配的短标题。
- [ ] 是否误把“显示说明”“操作说明”“数据流转”“异常”等示例当成固定栏目。
- [ ] Skill3/4/5 是否按现有 `display` / `operation` 展示，没有引入未迁移的 `logicSections`。
